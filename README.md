# Аналіз даних Prozorro

Застосунок призначений для завантаження, збереження та аналізу тендерів із публічного програмного інтерфейсу Prozorro. Проєкт зосереджений на закупівлях електричної енергії за кодом CPV `09310000-5` за грудень 2025 року, але критерії відбору можна змінювати через програмний інтерфейс або вебінтерфейс.

## Які Дані Завантажуються

Дані беруться з публічного програмного інтерфейсу Prozorro:

```text
https://public-api.prozorro.gov.ua/api/2.5/
```

Початковий перелік тендерів запитується так:

```http
GET /tenders?descending=1&limit=500&opt_fields=status,dateCreated,public_modified
```

З отриманого переліку обираються тільки ті тендери, які відповідають заданим критеріям. Для кожного такого тендера окремо завантажуються повні дані:

```http
GET /tenders/{tenderId}
```

У базу даних зберігаються нормалізовані дані:

- тендер: ідентифікатор Prozorro, статус, дата створення, замовник, очікувана сума, валюта;
- предмети закупівлі: код CPV і опис;
- договори: ідентифікатор договору, ідентифікатор рішення про визначення переможця, сума, валюта, дата підписання;
- постачальники: назва, тип ідентифікатора, значення ідентифікатора;
- зв'язок тендера з постачальником через ідентифікатор рішення про визначення переможця;
- сирий JSON-вміст у `jsonb` для перевірки, аудиту та можливості повторного розбору;
- стани задач завантаження та покажчики синхронізації.

## Критерії Відбору

За замовчуванням застосунок аналізує:

- `classificationId`: `09310000-5`;
- `createdFrom`: `2025-12-01`;
- `createdTo`: `2026-01-01`;
- `status`: тільки завершені тендери `complete`.

Фільтр за CPV перевіряється за полем `items[].classification.id` у повних даних тендера. Якщо у тендері немає потрібного коду CPV, він пропускається.

## Як Працює Завантаження

Завантаження запускається як фонова задача через програмний інтерфейс. Маршрут одразу повертає відповідь `202 Accepted`, а саме завантаження виконується у фоновій службі.

### Завантаження Від Новіших До Старіших

`Backward` - основний режим для тестового завдання. Він починає роботу з актуального переліку:

```http
/tenders?descending=1
```

Після цього завантаження переходить за `next_page.uri`, який повертає Prozorro. Саме цей режим використовується кнопкою **Оновити** у вебінтерфейсі.

### Завантаження Від Старіших До Новіших

`Forward` залишений у серверній частині як технічний режим для подальшої синхронізації. Він використовує збережені покажчики з `import_sync_states`, щоб завантажувати наступні сторінки після попереднього запуску.

У вебінтерфейсі цей режим не винесений окремою кнопкою, щоб поведінка відповідала очікуванню технічного завдання: користувач натискає **Оновити**, і система запускає завантаження даних.

### Повторний Запуск Після Зупинки

Задачі завантаження зберігаються у базі даних. Якщо серверний застосунок зупинився під час завантаження, незавершені задачі після повторного запуску повертаються в чергу і виконуються знову, а не залишаються помилковими лише через зупинку застосунку.

## Архітектура

Проєкт побудований за принципами чистої архітектури:

- `src/ProzorroDataMining.Domain` - доменні сутності та перелічення;
- `src/ProzorroDataMining.Application` - сценарії використання, об'єкти передавання даних, інтерфейси, прикладні служби;
- `src/ProzorroDataMining.Infrastructure` - EF Core, Dapper, PostgreSQL, клієнт програмного інтерфейсу Prozorro, сховища, черга завантаження;
- `src/ProzorroDataMining.Api` - мінімальні маршрути ASP.NET Core, налаштування залежностей, перевірки стану, обробка винятків;
- `src/ProzorroDataMining.Web` - панель керування на React.

Використані підходи:

- сховище даних через відповідний шаблон доступу;
- шар служб;
- одиниця роботи через `ApplicationDbContext`;
- фонова обробка через `BackgroundService`;
- `HttpClientFactory` для зовнішніх запитів;
- Dapper для аналітичних SQL-запитів;
- EF Core для збереження даних і міграцій.

## База Даних

Використовується PostgreSQL. Схема нормалізована для аналітики:

- `tenders`;
- `tender_items`;
- `tender_contracts`;
- `suppliers`;
- `tender_suppliers`;
- `tender_import_payloads`;
- `import_sync_states`;
- `tender_import_jobs`.

Важливі рішення:

- `TenderItem.Description` має тип `text`, бо поле не індексується і не використовується для групування;
- сирий JSON зберігається в `jsonb`, але аналітика працює за нормалізованими таблицями;
- `TenderStatus` зберігається як перелічення через числове перетворення;
- `ProzorroId` має унікальний індекс;
- для відбору за CPV є індекси на `tender_items.ClassificationId` і складений індекс `ClassificationId + TenderId`;
- для договорів є індекс `TenderId + AwardId`, щоб точніше пов'язувати договори з постачальниками через рішення про визначення переможця.

## Рішення Для Продуктивності

Проєкт містить кілька рішень з прицілом на великі обсяги даних:

- список тендерів використовує посторінкову навігацію за ключем замість `OFFSET`;
- `/api/tenders/list` повертає легке подання без повного завантаження `items/contracts/suppliers` через EF `Include`;
- повні дані тендера завантажуються окремо через `/api/tenders/{id}` тільки після вибору тендера у вебінтерфейсі;
- аналітичні підсумки обчислюються через Dapper і SQL;
- для завантаження повних даних тендерів використовується контрольована паралельність;
- зовнішні запити проходять через обмеження частоти;
- для `429`, `408`, `5xx`, перевищення часу очікування і мережевих помилок налаштовані повторні спроби;
- EF-запити з кількома колекціями використовують `AsSplitQuery()`.

## Обробка Помилок

Мережеві помилки під час роботи з Prozorro обробляються через політику повторних спроб Polly.

Повторюються запити після таких помилок:

- `HttpRequestException`;
- `TaskCanceledException`;
- HTTP `408 Request Timeout`;
- HTTP `429 Too Many Requests`;
- HTTP `5xx`.

JSON читається обережно:

- якщо немає `items`, `contracts` або `awards`, використовується порожня колекція;
- якщо немає назви постачальника, постачальник пропускається;
- якщо JSON невалідний або не містить `data.id`, тендер пропускається;
- невідомий статус відображається як `TenderStatus.Unknown`.

Необроблені винятки записуються через Serilog і повертаються як відповідь Problem Details.

## Маршрути Програмного Інтерфейсу

### Стан Системи

```http
GET /api/health
GET /api/health/ready
```

### Завантаження

```http
POST /api/import/tenders
GET /api/import/tenders/jobs/status?limit=10
GET /api/import/tenders/jobs/{jobId}
```

Параметри `POST /api/import/tenders`:

| Параметр | Типове Значення | Опис |
|---|---:|---|
| `classificationId` | `09310000-5` | Код CPV для відбору |
| `createdFrom` | `2025-12-01` | Початок періоду |
| `createdTo` | `2026-01-01` | Кінець періоду, не включно |
| `maxPages` | `20` | Найбільша кількість сторінок переліку |
| `pageSize` | `500` | Розмір сторінки переліку Prozorro |
| `direction` | `Backward` | Напрям завантаження |

Приклад:

```powershell
Invoke-RestMethod -Method Post -Uri "http://localhost:5095/api/import/tenders?classificationId=09310000-5&createdFrom=2025-12-01&createdTo=2026-01-01&maxPages=20&pageSize=500&direction=Backward"
```

## Перевірки Стану

`/api/health` - перевірка, що процес серверного застосунку працює. Вона не перевіряє базу даних.

```json
{ "status": "Healthy" }
```

`/api/health/ready` - перевірка готовності застосунку до роботи. Вона перевіряє підключення до PostgreSQL.

```json
{ "status": "Ready" }
```

Перевірка стану контейнера серверного застосунку використовує `/api/health`, щоб контейнер не позначався як несправний лише через тимчасову недоступність бази даних після запуску.

## Відомі Обмеження

- Черга завантаження працює всередині процесу через `BackgroundService`; стани задач зберігаються у базі даних, але це не розподілена черга.
- Якщо один запит повних даних остаточно падає після повторних спроб, поточна задача завантаження переходить у стан `Failed`. Для промислового використання можна додати режим часткових помилок і продовжувати завантаження інших тендерів.
- Посторінкова навігація за покажчиком добре масштабується вперед і назад у вебінтерфейсі, але не дає прямого переходу на довільну сторінку за номером.
- Аналітика обчислюється під час запиту. Для дуже великих обсягів можна додати матеріалізовані подання або фонове попереднє обчислення підсумків.
- Поточний Docker Compose використовує облікові дані для розробки PostgreSQL. Для промислового середовища їх треба винести в таємниці або змінні середовища.
- Вебінтерфейс не має окремої авторизації, бо це тестове аналітичне завдання.
